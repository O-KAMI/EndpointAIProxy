# 恢复后的状态核对

备份恢复到空库并通过校验，只说明归档可读、摘要及目标 schema 符合检查。归档是备份时点的数据；若备份之后服务继续运行，恢复库可能缺少之后签发的策略版本、凭据轮换或吊销、命令与回执，以及防重放记录。不能仅凭恢复库推断这些变化不存在，也不能仅凭“恢复验证通过”把客户端流量切入恢复库。

在隔离环境中恢复后，先保持客户端入口关闭，使用独立、可信且完整的备份后审计、数据库日志及终端证据核对策略版本上界、设备凭据与吊销、未完成命令和重放窗口。核对来源的覆盖范围、时间和完整性；如果无法确定真实最高已签发版本或其他关键变化，保持恢复目标隔离，不能假设备份中的最大版本足够。恢复过程中不要通过清除客户端状态或重复执行结果未知的命令来掩盖不一致。

版本号、凭据或命令状态一旦落后，正常发布或自动重试可能无法让终端接受期望策略，或导致认证失败和不安全的重复操作。具体恢复操作必须基于可验证的完整水位与运行记录制定，并在隔离环境完成演练及核对；仅提高版本也不能恢复丢失的凭据、命令和审计。当前仓库没有独立于数据库的不可回滚版本水位或自动对账机制，完整灾备与恢复验收尚未完成。

若已从独立、完整证据确认所有已签发策略的最高版本，可在**独立恢复库**且所有应用实例停用时，使用维护命令提升恢复库全局策略版本，并记录操作人、提供的上界及非敏感证据编号：

```text
python manage.py advance-restored-watermark --env sit --target-database restored_database \
  --verified-issued-max 12345 --actor operator --evidence-reference audit-record-id \
  --service-stopped --confirm-restored-target
```

以上数字、库名、操作人和证据编号只是示例。配置仍指向源库所在 MySQL 实例，目标库名必须与配置源库不同；`--service-stopped` 与 `--confirm-restored-target` 是操作方声明，程序不能验证所有实例已停止或目标真正隔离。工具检查 schema，在一个事务中锁定策略，拒绝仍有活动的策略批次，将版本推进至高于所提供上界及恢复库内现有水位，并与审计一起提交。证据编号不得包含密钥或凭据。若上界不完整或未知，不得猜测后执行；工具无法验证输入证据的真实性，也不处理丢失的凭据、命令、防重放或审计，不能作为切流许可。

本机隔离 MySQL 使用真实备份、备份后发布新策略、恢复到另一个空库并执行维护命令的测试，验证了恢复库版本可能低于备份后已签发版本，并在提供测试上界后仅将恢复库版本推进至该上界之上。额外测试覆盖数据库内部更高水位、活动批次阻断、策略状态不一致、无效参数和审计失败回滚。Windows 测试替代了缺失的 Linux 文件锁，不能代表 Linux 备份锁或生产恢复演练。

防重放记录同样可能落后：隔离测试中，备份后已在源库登记的合成加密请求，在其时间戳仍有效时可在旧备份恢复库再次登记。当前传输协议接受服务端时间前后 300 秒的时间戳，防重放记录保留 11 分钟。若无法恢复完整的备份后登记记录，恢复目标必须保持控制入口隔离；在确认旧服务最后一次可能接受请求的时间、所有相关服务时钟准确且不会回拨后，至少等待 11 分钟，并独立验证旧请求已不再可接受，才能消除这些已接受请求在该协议时间窗口内的重放风险。若最后接受时间或时钟不可确认，就不能把等待时间当成已完成验证。

等待窗口只针对上述已有请求的时间有效期，不会恢复缺失的凭据、吊销、命令和审计，也不能阻止持有仍有效密钥者构造新请求。凭据及密钥泄露、吊销和轮换仍须独立对账；未知结果的命令须人工核验。入口隔离措施需要由有相应权限的管理方实施，不能假定当前普通账号能够完成。
