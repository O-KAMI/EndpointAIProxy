# 共享传输密钥轮换（隔离验收候选）

0.1.26 候选控制端可以同时接受两把不同的 AES 传输密钥，并使用请求所用的密钥
加密响应。默认只接受原有主密钥；新增密钥必须同时设置 ID 和 Base64 编码的
32 字节随机密钥，ID 仅可使用字母、数字、下划线及连字符，且不得与主密钥重复。
两把密钥的内容也必须不同。旧协议客户端无需修改。

控制服务的 `start.py` 从受保护的 `launch-env.json` 读取配置。下列字段只展示
名称和占位符，应由有权人员在受保护的本地配置中填写，不得放入源码或日志：

```json
{
  "SF_CONTROL_TRANSPORT_KEY_ID": "CURRENT_KEY_ID",
  "SF_CONTROL_TRANSPORT_KEY": "CURRENT_BASE64_KEY",
  "SF_CONTROL_TRANSPORT_ADDITIONAL_KEY_ID": "NEXT_KEY_ID",
  "SF_CONTROL_TRANSPORT_ADDITIONAL_KEY": "NEXT_BASE64_KEY"
}
```

这是现有配置中的四个相关字段示意，不是完整的启动配置。禁止用示例值生成正式包。
先在隔离环境验证 schema 升级、回退和以下流程；0.1.26 正式更新入口仍受原有门禁限制。
`manage.py secrets` 依赖 POSIX 权限保障，在 Windows 上会拒绝生成文件；应在有权限的
隔离控制服务环境生成并妥善保管，不需要 root，但目标目录必须只有授权用户可访问。

1. 备份现有配置和数据库，准备新随机密钥及独立的安全交付渠道。主密钥保持原值，
   在所有提供终端接口的实例增加新密钥，并完成受控重启和逐实例双密钥验证。
   在所有实例就绪之前不要分发新密钥，否则请求可能随机失败。
2. 分批构建并交付使用新密钥的客户端，验证既有设备凭据、策略、心跳和离线恢复。
   记录成功迁移的设备和仍离线的设备；不能用重新注册或清库掩盖失败。
3. 确认所有实例及回滚路径均能识别两把密钥后，可将新密钥设为主密钥、旧密钥
   设为附加密钥。变更所有实例并验证新旧客户端。主附加位置不改变线上的密钥 ID。
4. 仅在明确处理离线设备、回滚和历史安装包后，在所有实例移除旧密钥并验证旧
   请求被拒绝；保留受控的恢复方案。隔离期与退役时间由实际终端覆盖情况决定。

这仅支持**共享密钥**分批轮换，并不能消除单个终端泄露共享密钥的影响；设备级
可轮换传输身份仍未实现。TLS、服务端私钥签名和设备凭据迁移各有独立验收要求。
本机隔离 MySQL 与回环 HTTP 联调中，旧 .NET 客户端在主密钥和附加密钥并存时
完成注册、策略、心跳、事件及启停命令回执；该验证未覆盖 Linux Gunicorn、多进程、
实际网络和已部署终端，也不证明安全迁移或轮换操作已完成。
