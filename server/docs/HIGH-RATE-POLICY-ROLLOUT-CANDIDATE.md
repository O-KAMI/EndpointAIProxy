# 高速策略批次候选：仅供隔离验收

默认每批上限仍为 20 台/秒。候选控制端可通过 `SF_CONTROL_POLICY_ROLLOUT_MAX_RATE` 显式设置 1～5000；超过 20 才使用批量路径。管理进程、所有工作进程必须使用相同候选代码和同一上限。不要把高速批次交给旧工作进程；升级、降级和混合版本均须先在隔离环境验证。配置超过 20 时，启动检查要求待处理目标索引完整且可见；创建和恢复批次仍要求可见的策略版本索引。上限被降低时，运行中的超限批次会暂停并记录审计，不能直接恢复。

每次事务锁定全局策略和批次，最多处理 250 台；逐台检查设备凭据、协议和已有覆盖策略，为成功目标分配不同且递增的版本，并在同一事务中写入策略及目标状态。暂停等待当前事务提交后阻止后续批次；全局策略锁持有时间可能影响其他策略操作。速率是每批平均上限，允许最多一批突发；实际数据库耗时降低速率，失败和慢事务不积累追赶额度。此路径必须与共享策略版本水位的当前代码一起部署，不能只替换单个文件。

单事务内相同覆盖策略复用校验结果；不同覆盖及无效策略分别处理，版本仍逐台检查和分配。隔离 MySQL 的 1 万目标单次实验中，修改前分配约 10.612 秒，修改后另一次约 8.673 秒；机器与缓存状态可能不同，不能将差异作为稳定收益或容量结论。分阶段采样可使用探针的 `--policy-profile`；SQL 计时不包含全部 Python 处理、事务提交和工作线程等待。

批量目标状态更新使用参数化 `JSON_TABLE` 与目标主键关联，避免每行重复遍历多个 CASE 分支；事务内写入、逐台状态及错误码保持原有语义。当前代码的本机隔离 MySQL 8.0.28 单次实验：10 万合成目标创建约 6.924 秒，400 批按工作线程等待规则分配约 51.651 秒，核对 10 万个不同分配版本；未包含 HTTP、并发心跳、远端数据库、真实终端或回执。该次 SQL 采样中策略状态写入累计约 8.128 秒、目标更新约 8.087 秒。机器和缓存状态与其他实验不同，不能将耗时差直接归因于代码，也不能据此判断 p95、容量或端到端收敛。

策略分配与设备凭据恢复统一为先锁心跳再锁凭据。隔离 MySQL 以可控并发覆盖了低速、高速分配与凭据恢复的锁顺序，以及高速分配和真实心跳更新同时运行；这是少量设备的正确性检查，不代表 10 万设备并发性能或不存在其他死锁。

校验复用之前、当前锁顺序下的本机隔离 MySQL 8.0.28 单次实验：10 万合成目标、显式上限 5000 台/秒、单工作线程按应用的等待规则，创建目标约 18.185 秒，400 批共分配 10 万目标约 205.241 秒，核对到 10 万个不同的分配版本。锁顺序修改前另一次实验分别约 8.119 秒和 101.554 秒；运行时机器及缓存条件不同，不能据此将差异归因于锁顺序。该实验单是创建和分配就超过 120 秒，且没有 HTTP、并发心跳、远端数据库、真实终端、校准或回执，未达到端到端时效目标。最后一批分配后，批次状态还需后续工作线程轮询才转为下发完成。少量样本不是 p95 或容量验收。

隔离探针可用 `--policy-rollout-targets 100000 --policy-rollout-dispatches 400 --policy-rate 5000 --policy-respect-rate`；必须同时指定与生产隔离的 MySQL 和合成数据，详见 `ISOLATED-LOAD-TOOL.md`。未加 `--policy-respect-rate` 会强制跳过限速，只可用于事务成本实验。完成混合负载、策略版本与签名兼容、锁等待、故障恢复、8 小时长稳和真实终端回执验收前，不得提高现网限速。

隔离探针可再加 `--policy-heartbeat-workers 8 --policy-heartbeat-rps 1000`，只并发执行合成心跳表的行更新，不运行完整心跳事务、HTTP、加密或终端。它报告请求频率、实际完成数、调度遗漏和更新延迟，不能用请求频率代替实际负载。一个本机单次实验中，1 万目标分配约 8.640 秒，请求每秒 1000 次行更新，完成 6085 次、遗漏 2554 次调度；另一次请求每秒 500 次，约 7.976 秒分配期间完成 3475 次、遗漏 511 次。生成器与数据库共用本机，不能区分瓶颈，更不能作为 10 万在线容量验收。工作线程无法停止时保留随机测试库，避免删除活动数据库。
