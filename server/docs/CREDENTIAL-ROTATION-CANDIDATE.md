旧交付材料为 0.2.19，当前客户端验收候选为 0.2.20；本机全量 Go 测试、vet、未签名 MSI

## 协议与持久化

客户端先在平台保护的本地状态中保存随机 32 字节新 Token、轮换 UUID、服务身份和
旧 Token 摘要，然后才能发出准备请求。当前计划周期为 30 天，由服务端心跳响应
通过 `credentialRotationV1.minAgeSeconds` 协商；客户端必须使用响应中的服务器时间。
旧客户端未声明支持时不发送该能力，HTTP 或共享封装也不能调用更新接口。

两个端点均只接受 HTTPS 下与目标设备绑定的 V2 信封：

| 端点 | 认证与输入 | 结果 |
| --- | --- | --- |
| `POST /api/v2/devices/{id}/credential/prepare` | 当前主 Token；`rotationId`、`nextDeviceToken` | 准备新 Token 验证值，返回新设备封装及截止时间 |
| `POST /api/v2/devices/{id}/credential/commit` | 新 Token 和对应的新设备封装；`rotationId` | 激活新 Token，旧 Token 留有 24 小时重叠窗口 |

准备状态有效期 24 小时，旧 Token 在准备阶段继续有效；同一轮换 UUID 与不同材料
冲突，另一个未结束轮换不能覆盖现有状态。准备响应丢失可按同一材料重试，不延长
当前有效期；过期后仍持有主凭据的客户端可以重新准备。提交需证明持有新 Token，
重复提交不会重复审计或延长重叠窗口。已激活且当前 Token 有效时，提交接口可确认
其当前有效性，包括临时状态已经清理的情况；这不重建任意历史轮换的证明。

服务端每台设备至多保留一行状态，只存 Token 验证值；设备封装最多尝试两个验证值，
解封后仍要求信封绑定的 Token 与选中的验证值一致。防重放继续先于业务独立提交。
设备吊销拒绝全部凭据，受控恢复或旧协议的凭据替换会在原事务内清除轮换状态。
每次维护至多删除 1000 条过期状态，每进程每分钟调用一次；多个进程的清理预算会叠加。
清理使用独立数据库锁，不能将此单次上限表述为全服务每分钟上限，不在心跳请求中清理。

停用开关只阻止新的准备，同一份有效准备结果仍允许幂等取回并完成，重叠凭据仍按期限校验。紧急失效
必须使用既有吊销或受控恢复流程，不能把停用开关视为撤销已发凭据。

## 数据库和回退边界

schema 5 为原基础结构。显式维护 `manage.py ensure-credential-rotation --env sit
--service-stopped` 增加 InnoDB 状态表，并把版本标记提升为 schema 6；需要先完成
基础迁移，所有服务进程必须停止。这里只描述隔离验证流程，当前不要在现网执行。

schema 6 标记与基础 SQL 和新增 DDL 一同校验。旧控制端按版本与校验和拒绝启动，
既有“未使用批次回退”命令也不能把 schema 6 降回旧版。关闭新准备后仍保留
schema 6 和已有状态；不能直接换回 r75 或更早服务程序。中断后仅有空表且仍为
schema 5 的维护可恢复；存在状态却没有相应版本标记时拒绝就绪。

旧客户端不会恢复新增的本地待轮换记录。启用后若要回退客户端，须先停止新准备并独立
确认目标设备全部完成轮换，或完成经过验证的人工凭据恢复；不能靠删本地状态、降级或
重新注册掩盖未完成轮换。无法确认时向前修复。

这张表是凭据状态，不能像派生搜索索引那样在恢复时忽略。备份即使在开关关闭时也
包含 schema 6 的轮换状态；启用更新的目标配置会在写入目标前拒绝缺少该状态的
旧备份。旧备份是否丢失已签发凭据仍需独立对账，版本和摘要不能单独证明恢复安全。

## 客户端实现与剩余门禁

- Go 工作树已实现能力协商、服务器时间判定到期、随机新凭据预持久化、新旧封装切换与退避；
  未完成轮换时禁止自动重新注册。新 Token、封装状态和清除待更新状态在同一 SQLite 事务内提交，
  使用旧凭据、待更新记录和服务身份的比较检查，拒绝覆盖并发恢复结果。
- 定向 Go 测试已覆盖受保护状态重启、事务中断、身份不匹配和应用禁止重新注册。
  受控恢复在校验新凭据后，原子更新凭据并清理旧传输绑定和待轮换记录；失败时保留原状态。
- 最终包的独立终端、Linux 与 8 小时等既有门禁仍未通过；Mac 正式签名、公证由团队执行。

此更新不增加设备独立私钥或硬件设备证明，也不提供本地整个状态库被删除或回滚的防护。
