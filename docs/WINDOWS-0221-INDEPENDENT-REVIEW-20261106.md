# Windows 0.2.21 r2 独立验收复核

本文是冻结 0.2.21 的审计结论，不随后续修复改写证据。版本字符串门禁、状态与采样的
后续处理见[0.2.22 复测边界](CLIENT-0222-ADDITIONAL-ACCEPTANCE.md)和
[当前交付结果](OPTIMIZATION-CURRENT-RESULT.md)；历史问题已被新候选处理不等于原生重验通过。

日期：2026-11-06。复核对象为 WIN11-X64-A 的脱敏回传包，结合冻结构建输入与当前
Go 源码核查。未在构建机安装 MSI，未修改真实用户配置、客户端程序或灰度服务。

## 结论

**Win11 基础链路与低负载运行有有效进展，整体仍不放行；DSH 推理接管子项应判不通过。**
测试方总计 11 PASS / 0 FAIL / 5 BLOCKED / 1 NOT-APPLICABLE；这个计数隐藏了
APP-01 内部 DSH 的实际异常，不能用“FAIL 0”解释为没有功能缺陷。Codex CLI、Claude
及协议级请求的成功，不替代 DSH 应用本身的推理路径验证。

回传包 SHA-256：
`e292dce5bdc3355980339b6bb2a6079ccfc0f8ae62d1f36ef786f94a838d5bf0`。
ZIP CRC 通过，84 个文件中 83 个受清单覆盖，摘要全部一致；剩余文件为清单自身。
MSI 与服务程序摘要匹配已冻结 0.2.21 r2。212 个构建源输入与本机当前文件再次全部匹配。
这说明测试绑定了指定候选，不能单凭 `sourceCommit` 重建含未提交输入的历史包。
原始 ZIP、解包证据和重算结果保存在工作区受限目录，不随 Git 提交。

### DSH 缺陷能确定到哪一层

源码不是只遍历 desktop：通用实现遍历多个 profile；但它要求明确的 provider/baseURL，
且只接受 alpha.5。桌面账户专用实现只针对 desktop，改写 `deepseek-account.inferenceOrigin`
与 `llm-deepseek-account.baseURL`，只接受 rc.2/rc.3。空补丁、默认 provider、不同凭据形态
不能据此视为受管。因此“所有非 desktop profile 都因未遍历而旁路”这个根因描述不准确。

重启后 `/models` 经代理、真实推理仍未捕获，足以阻断本次 DSH 接管验收；但具体是所选
API-key provider、账户插件、默认配置层还是其他运行路径，需要有效 provider 的脱敏结构
与调用路径才能定因。不能仅凭对外 443 连接和零审计错误，就证明所有字节的最终目的地。
审计错误计数为零，也不证明没有未接管流量。

下一轮只需保留实际 provider/插件名称、版本、profile 与配置层来源、地址形态、进程启动
时间以及匹配测试轮次的捕获摘要；不要回传凭据、账户授权文件或真实对话正文。
区分“配置已写入”“等待应用重新加载”“已经观察到推理经过代理”，不能以 `/models`
成功或配置状态 managed 代替最后一项。新建会话和真实重启后的推理都须复测。

### 问题一：升级是否被版本门禁阻止

是。`configuration/dsh.go` 要求 `DSHSupportedVersion == 0.2.1-alpha.5`，自定义
provider 还要求 pi-ai 1.3.0；`contracts/dsh.go` 的账户路径只接受 rc.2、rc.3，
`discovery/dsh_desktop.go` 还核对四个内置插件与桌面版本一致。rc.4 或正式 0.2.1
不会因为配置长得相同而自动被接受，已有测试明确断言这些版本不支持。

这影响新接管及后续维护；不能简单说应用升级立即让所有已有流量停代。
已写入的配置和已有路由可能仍保留，必须分别核对，不能靠清状态库或重注册恢复。

### 问题二：恢复配置是否会与校准互抢

| 实际路径 | 当前行为 |
| --- | --- |
| 控制端离线 | 继续有效缓存，不自动恢复直连；本次 OFF-01 证实的是这条路径 |
| 网关连接异常 | `proxy.go` 返回 `502 GATEWAY_CONNECTION_FAILED`，不改配置、不自动改走原厂 |
| 正式远程暂停 | `operationOnce` 在同一 mutation 锁内先持久停用状态再 `DetachAll`；`Reconcile` 检查 `Enabled()` 后退出，不会重新接管 |
| 独立临时 detach | 管理接口只调用 `DetachAll`，未保存停用状态；后续 `Reconcile` 可重新接管。该接口默认未启用，不应描述为现网已发生反复抢配置 |
| 离线维护解除/卸载 | 要求停服务；服务的周期协程不在运行。正常服务退出本身不等于卸载，也不保证自动恢复配置 |

在私有 Go overlay 测试中，临时 detach 后主动连续执行校准，配置重新指向本地；通过
正式停用路径后连续校准，配置保持原厂。测试仅使用临时合成用户目录，不修改候选源码。

若建设自动降级，周期任务应继续健康探测，但暂停配置接管写入；恢复须连续健康、经过
冷却期并检查配置所有权及用户修改。不要在单个 401/429、策略拒绝或任意上游错误后
自动旁路；不要把已提交或已开始 SSE 的非幂等请求静默重发。具体故障放行条件仍须明确。

## 证据修正与剩余验收

- `trend-analysis.json` 的 `observerTrends.workingSetMB/privateMB.slopes` 实际仍是
  bytes/hour，字段名容易被当成 MiB/hour；已按原始样本重算。部分旧 issue 状态和 CSV
  的总结仍保留过时文字，应以本次明细和统一状态表为准，保留历史但标注被取代。
- `rounds.sanitized.json` 的策略 T0 是请求返回附近时刻，CSV 使用发起时间；相差约
  0.05～0.43 秒。本次仍全部在 120 秒内，不改变本设备结论；命令也需统一发起、执行
  结束、回执可见三个时间，不能将 `completedAtUtc` 与查询看见的时间混作同一指标。
- 报告称摘要索引存在“检查点滞后”，但源码使用 O_SYNC 逐条写入，无应用层延迟批量刷新。
  应核对取证副本时间、复制工具缓存、是否读到当前源文件；目前不能定性为客户端缓存缺陷。
- 合成长稳工具已有独立交付 ZIP，并非需重新开发；本次重新核对 ZIP CRC、脚本和
  `soak-control.exe` 均在。需重新向测试团队交付，Python 3.13+ 与空闲端口窗口仍由
  团队准备；不能为抢 18080 停止他人在用服务。
- 未关闭：干净首装、旧 .NET 升级、IOA、第二用户、Codex Desktop、CC Switch、
  资产重启前对照/旧协议、队列容量边界与离线投递、合成八小时、磁盘总量证据。
  Win10、Mac ARM64/Intel 和控制端十万在线不由本包证明。
- 报告另记录了测试会话出现提权口令并被模型回显。按该报告处理为需立即轮换相关
  口令的事件；本次未获得原始正文，未自行更改终端账号，也不把它描述为已独立复现。

本次相关 contracts/configuration/app/proxy 测试通过，包含临时 detach 与持久停用的
两项行为复现；一个符号链接用例因当前 Windows 缺少权限跳过。测试通过说明符合当前
实现，不能关闭上述真实 DSH 和未实现的自动降级问题。冻结 MSI 未修改、未重建。
