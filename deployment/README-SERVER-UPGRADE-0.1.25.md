# 0.1.24 → 0.1.25 单终端策略升级（候选，未放行）

仅适用于 appdeploy、Python 3.13.15、未由 systemd 托管的 0.1.24/schema 2。
0.1.25 新增 schema 3 单终端策略，不可使用旧 0.1.24 的无迁移升级流程。
当前为本地候选，现场兼容及发布验收未完成。

同目录必须保留 update-server-0.1.25.py、update-server-0.1.24.py、更新 ZIP 和摘要。
0.1.24 脚本仅作为已验证的进程、权限、私有配置及解包辅助模块，不直接运行它升级到 0.1.25。
MySQL 工具目录需同时包含兼容的 mysqld、mysql、mysqldump，用于备份与隔离恢复验证。

```sh
python update-server-0.1.25.py --archive EndpointAIDLP-Server-0.1.25-update.zip --mysql-bin /path/to/verified/mysql/bin
python update-server-0.1.25.py --action status
```

升级先校验现役服务、精确 schema 2、包清单和离线依赖，准备新运行目录。
保留新版本 canonical SQL；继承私有配置、认证和原数据根，不生成凭据。
准备失败不停止旧服务。切换阶段停止全部旧实例，备份数据库与配置，再在密码保护的
临时 loopback MySQL 中恢复真实备份，比较策略摘要和业务表数量，并先演练 schema 3 迁移。
临时实例退出后才迁移现役数据库、启动新版并验证管理接口。
备份留在旧目录的 upgrade-backups 中，权限仅限部署账户。

## 回退边界

新迁移只增加 device_policy_state，不改已有业务表布局。
在尚未下发任何单终端策略时，失败恢复或以下命令会停止新版、确认新表为空，
解除空表及版本标记变更后启动旧版。不会用旧备份覆盖现有业务记录，避免丢失新到的心跳和回执。

```sh
python update-server-0.1.25.py --action rollback
```

一旦新增表存在任何记录（包括恢复继承留下的版本记录），回退旧代码被拒绝并恢复新版运行。
此时应保留 schema 3 与版本记录修复新版，不得删除覆盖记录、改 schema 标记、
直接启动 0.1.24 或用历史备份覆盖现役业务表。
这是客户端策略版本单调性的要求；恢复继承不能返回较低的全局版本。

不得运行 init-db。迁移及升级失败时保留目录和备份，先检查固定阶段与脱敏结果。
生产迁移前必须通过隔离 Linux 的多 worker 加密请求、迁移、备份恢复和回退回归。
测试使用冻结的公开 0.1.24 源码副本，不把现役私有配置目录当作测试基线。
