# 0.1.26 控制端升级候选：尚不可执行切换

本目录的升级器是待验证的候选实现，不是发行包。`MUTATION_VALIDATED` 固定为
`False`，更新和回退入口都会拒绝执行；打包脚本也会拒绝生成 0.1.26 交付包。
只有在隔离 Linux 环境完成真实备份、恢复、升级、回退及故障注入后，才能审查并解除这些阻断。
不要在生产环境修改标志来绕过门禁。

Linux 指控制服务所在服务器的操作系统，与 Windows、Mac 客户端无关。候选流程使用
运行服务的普通账号，不要求服务器 root 或系统级 systemd 操作；它只覆盖现有由该账号
直接启动、未由 systemd 管理的 0.1.25 单角色 8080 服务，数据库为 schema 3。
运行器依赖旧服务虚拟环境中的 PyMySQL，应使用旧服务的 `.venv/bin/python` 执行。
其他部署方式、schema 4、管理账号模式和系统服务托管均需要单独验证，不能套用。

候选流程要求事先独立核验升级包 SHA-256，并确认停止全部其他数据库写入者；仅停止本机
进程不能证明其他服务器、管理脚本或任务没有写入。它在停服后备份，启动同账号的临时
本地 MySQL 恢复副本，逐行计算各原业务表的一致性摘要，在副本迁移至 schema 5 后再核对，
最后才迁移原库。恢复副本和备份包含真实敏感数据，必须放在受限目录并按实际数据保留
规则处理；磁盘空间检查只是最低门槛，无法保证解压和恢复所需空间足够。

自动回退只允许批次相关表没有数据且结构满足检查时恢复 schema 3；若已产生批次历史，
不能通过删除数据强行回退。异常时需保留目录、备份及日志，由运维按现场状态处理。
健康检查仅覆盖本机就绪、控制台和管理策略读取，不能证明外部 TLS、客户端连接或容量。

隔离 Linux 验收至少应覆盖 schema 3→5 与 schema 4→5 的迁移、原数据及版本水位核对、
备份恢复、空批次回退与非空批次拒绝回退、多进程、数据库断连、磁盘不足、启动失败和
失败后恢复，并在最终交付包上复验。schema 4→5 属于数据库迁移验收范围，并不意味着
此候选升级器已经支持从 0.1.25 以外的部署状态执行切换。容量、混合流量及 8 小时长稳
需要独立测试，不能用此脚本的成功代替。
